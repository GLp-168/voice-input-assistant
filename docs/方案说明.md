# 语音转文字方案说明

## 项目目标

本项目希望提供一个离线优先的桌面语音输入助手，让用户在任意文本输入场景中通过语音快速输入文字。第一版重点验证核心链路：用户触发录音，系统采集语音，完成本地转写，然后把文本输出到目标输入区域。

“离线优先”意味着第一版不依赖云端 ASR 服务作为必需能力。真实模型可以按业务要求在后续接入，本项目骨架会保持 ASR 引擎可替换，避免把某一个大模型包写死在基础依赖中。

## 第一版功能范围

第一版建议聚焦以下能力：

- 基础启动入口：提供命令行或轻量桌面入口，验证程序能在目标机器启动。
- 录音触发：支持手动开始和结束录音；Windows 预览包已接入全局热键，默认 `Ctrl+Shift+F8`。
- 音频采集：通过可选 `sounddevice` 和 `numpy` 完成麦克风采集、采样率配置和音频缓冲。
- ASR 适配层：定义统一接口，让 mock 引擎和真实离线 ASR 引擎都能接入。
- 文本输出：第一版支持剪贴板 + 粘贴热键注入，复杂业务系统稳定后再增加平台原生输入注入。
- 状态反馈：明确展示待机、录音中、转写中、完成和失败状态。

当前客户预览版已经具备 Windows 桌面窗口、Dummy ASR 演示闭环、FunASR 流式识别、离线高精度复核、VAD、标点、词库热词、长录制、剪贴板式文本注入、全局热键、系统托盘、运行日志、诊断工具和安装包。它适合验证产品形态、安装流程和真实本地识别链路；客户业务系统注入兼容性、国产系统打包和模型二进制适配仍需在目标环境继续验收。

## 用户使用流程

1. 用户打开语音输入助手。
2. 用户在需要输入文字的应用中定位光标。
3. 用户触发录音。
4. 用户说出内容并结束录音。
5. 系统在本地完成语音转文字。
6. 系统把文本复制到剪贴板或输入到当前应用。
7. 用户确认文本，必要时手动修改。

## 工程分层建议

- `audio`：负责设备枚举、录音、音频格式转换和基础异常处理。
- `asr`：负责 ASR 引擎接口、mock 引擎、真实模型适配和结果结构。
- `output`：负责剪贴板、模拟键入、平台输入注入等文本输出方式。
- `app`：负责用户入口、状态流转、配置加载和模块编排。
- `tests`：覆盖接口契约、状态流转和可替换实现。

基础依赖保持轻量，音频采集、剪贴板和开发测试能力通过 extras 安装：

- `voice-input-assistant[audio]`
- `voice-input-assistant[clipboard]`
- `voice-input-assistant[dev]`

## 接入真实 ASR 的路径

当前默认识别链路已经切换为 FunASR：实时链路使用 Paraformer streaming；录音结束后由独立进程使用离线 Paraformer + FSMN-VAD + CT-Transformer 标点复核；导入音频使用另一条按模式切换回收的离线进程。词库作为原生热词传入两阶段模型。不同模型组合应通过不同安装包交付，不在用户设置中暴露档位选择。

真实 ASR 建议按以下顺序继续推进：

1. 先定义 `Transcriber` 类接口或协议，输入为音频数据和采样率，输出为转写文本、置信度、分段信息和耗时。
2. 使用 mock transcriber 编写端到端流程测试，确保录音、状态流转和输出模块不依赖具体模型。
3. 默认实时链路采用 FunASR Paraformer streaming，停止后使用离线 Paraformer + FSMN-VAD + CT-Transformer 标点做高精度复核。
4. 词库会作为 FunASR 原生热词传入复核模型，同时保留文本层面的规范化纠错。
5. 在适配层中处理模型路径、设备选择、首次加载耗时、异常降级和日志。
6. 用短音频样本建立回归测试，覆盖中文普通话、数字、英文夹杂、静音和噪声场景。

这样可以把产品体验和模型实现解耦：前端入口、录音和文本输出可以稳定演进，ASR 引擎也可以按客户环境、硬件能力和授权要求替换。

## 当前两阶段架构

麦克风 PCM 在父进程只采集一次；每个音频块同时发送给 online worker 并写入会话临时 WAV。online final 到达后才允许启动 review 推理：`constrained`/`balanced` 先释放 online worker，`high_quality` 可以保留 online worker 驻留，但两者仍不并行推理。review 成功时整段替换 online 终稿；空结果、异常、超时或取消时保留 online final，并把完成状态标为不完整。临时 WAV 在正常完成、取消和异常路径均清理。

音频导入与流式复核不同时保留各自的离线模型。切换到流式录音前会关闭导入链路的 idle worker；切换到音频导入前会关闭保留的流式 online/review worker。Sherpa 和 FunASR 子进程都强制使用资源档位给出的线程预算，外部 `OMP_NUM_THREADS`/`MKL_NUM_THREADS` 不会绕过限制。

## 2026-08-03 工程基准

当前 5 条 WAV 仅作为提交级 smoke gate，不代表正式模型选型。两阶段报告位于 `tmp/streaming_eval_samples/p2_two_stage_eval_20260803.json`：

| 指标 | 结果 |
| --- | ---: |
| raw preview CER | 4.878% |
| raw online-final CER | 1.626% |
| raw review-final CER | 0% |
| post-lexicon preview CER | 4.065% |
| online/review 热词召回 | 86.67% / 100% |
| 首个非空预览平均值 | 1.052 s |
| online 冷启动 ready | 14.30 s |
| 首次 review 额外等待 | 33.90-34.42 s |
| 后续 review 额外等待 | 0.74-0.91 s |

本机进程树观测值约为：`balanced` 在 review 前释放 online 后约 3.70 GiB，`high_quality` 双 worker 驻留约 4.31 GiB。它们分别比早期约 6.17 GiB 峰值低约 40% 和 30%，但这不是跨硬件保证。独立离线进程把首次 review 冷加载延长到约 34 秒，这是当前最明确的剩余体验成本，界面必须持续显示“正在整理文字”进度，不能伪装成无等待。

## 正式引擎选型门禁

正式比较保留四组候选：FunASR Python、固定版本 FunASR Runtime、Sherpa-ONNX INT8、ONNX Runtime Paraformer FP32/动态 INT8/校准 INT8。每个候选必须同时跑 online 公平赛道和完整产品赛道；online 赛道关闭文本替换，仅保留同一热词偏置，产品赛道分别报告 online-final 与 review-final。

统一记录 raw preview/online-final/review-final CER、post-lexicon CER、热词召回、cold/warm ready、首字、停止到两种 final、RTF、完整进程树 RSS、关闭后残留、安装体积和稳定性。提交级硬门禁为首字 P95 不高于 1.5 秒、弱机 online RTF P95 不高于 0.8、热词召回不低于 95%；正式语料必须覆盖安静办公、远场噪声、口音/中英混说和专业热词四个分层，总时长不少于 60 分钟。

## MVP 验收口径

第一版可按“可用闭环”验收，而不是按最终准确率验收：

- 程序能在目标系统启动。
- 用户能明确开始和结束一次录音。
- 录音数据能传入 ASR 适配层。
- ASR 适配层能返回文本结果或明确错误。
- 文本能通过至少一种方式输出给用户。
- 失败时有清晰提示，不静默丢失用户语音。

## 客户预览验收边界

真实测试前可先验收：

- Windows 安装包、免安装包、启动入口、卸载入口。
- GUI 基础操作、首次启动提示、运行日志、托盘和全局热键。
- Dummy ASR 闭环和文本展示。
- FunASR 模型、词库热词、音频转码和系统诊断工具。
- 麦克风、ASR、注入失败时的用户可见错误提示与日志记录。

必须等客户真实环境才能验收：

- 客户目标机器上的真实 ASR 准确率、延迟和模型加载表现。
- 客户业务系统输入框中的注入稳定性。
- 现场噪声、静音、权限限制、不同麦克风设备的体验。
- 麒麟、龙芯等国产系统安装包、运行时依赖和输入注入适配。

## 风险与应对

- 离线模型体积和首次加载时间可能影响体验：通过懒加载、进度提示和模型路径配置缓解。
- 不同平台输入注入能力差异较大：先用剪贴板输出建立通用闭环，再做平台适配。
- 麦克风权限和设备选择会造成部署问题：提供设备检测、错误提示和诊断日志。
- 真实环境噪声复杂：后续引入 VAD、降噪、热词和样本回归集。
